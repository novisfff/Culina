## BUG-001：侧边栏与家庭页的“本周协作”统计口径不一致

- 严重度：P2（跨页面同名统计互相矛盾，误导用户判断本周家庭协作情况）
- 修复方案确定性：98%
- 浏览器复现路径：使用 `linran` 登录桌面端（Chrome，当前自然视口）→ 在首页观察侧边栏“本周协作 0 次”→ 点击“家庭”→ 家庭概览显示“本周协作 1 次”。
- 预期结果：同一家庭、同一时刻、同名“本周协作”在侧边栏和家庭页使用同一业务周与同一协作事件口径。
- 实际结果：侧边栏使用 `/api/activity-highlights` 返回的家庭时区自然周高亮事件数；家庭页把 `/api/activity-logs` 中所有事件按滚动 7×24 小时重新计数，得到不同结果。
- 根因：`buildAppFamilyViewModel` 在前端重复定义了“本周”为滚动七天，并且计数了全部审计活动；后端已有 `activity_week_window_utc` 和 `week_highlight_count` 作为统一合同。
- 修复：家庭工作区也加载活动高亮摘要，并把 `week_highlight_count` 传给家庭页统计卡；活动日志仍只负责活动列表和当前用户近期记录，不再承担周统计。
- 自动化验证：新增模型回归用例，证明活动日志有 1 条但服务端周高亮为 0 时必须显示 0；同步更新工作区查询范围测试。
- 浏览器回归：Chrome 刷新后按“首页 → 读取侧边栏 → 家庭 → 读取统计卡”原路径复测；两处均为“本周协作 0 次”，控制台无 warning/error。

## BUG-002：已过期库存批次在食材详情中被标成“新鲜”

- 严重度：P1（过期食品被绿色“新鲜”状态误导，和同页提醒、库存工作区结论直接冲突）
- 修复方案确定性：99%
- 浏览器复现路径：Chrome 桌面端首页 → 全局搜索 → 输入“牛奶” → 点击食材结果“牛奶” → 查看“库存批次”。
- 预期结果：已超过到期日期且仍有剩余量的批次明确显示“已过期”，并使用过期视觉状态。
- 实际结果：同页显示“1 批已过期”、购买于 427 天前且默认保质期 3 天，但批次徽标仍显示“新鲜”；库存工作区也已将该批次判为过期。
- 根因：`InventoryItem.status` 表达批次的存储/开封状态，枚举本身没有 `expired`；`IngredientDetailView` 却直接用该字段渲染日期状态，没有像库存提醒模型一样根据 `expiry_date` 与家庭业务日派生过期状态。样式中已有 `tone-expired`，但此前从未被详情批次使用。
- 修复：详情批次在展示层先按 `expiry_date` 与 `businessDateKey()` 判定是否过期；过期时显示“已过期”并使用 `tone-expired`，未过期时保留原库存状态标签。
- 自动化验证：新增详情渲染回归用例，覆盖“持久化状态 fresh + 到期日已过 + 仍有剩余量”的真实冲突组合。
- 浏览器回归：按“首页 → 全局搜索‘牛奶’ → 点击食材结果 → 库存批次”原路径复测；桌面与移动详情 DOM 均显示“已过期”，卡片类均为 `tone-expired`，控制台无 warning/error。

## BUG-003：移动首页“新增食材”会重开上一次食材详情

- 严重度：P1（主入口执行了错误动作；用户无法从首页进入新增流程，并可能误以为正在编辑旧食材）
- 修复方案确定性：99%
- 浏览器复现路径：Chrome 390×844 → 首页全局搜索“牛奶”→ 打开并关闭“牛奶”食材详情 → 从移动底栏返回首页 → 点击“新增食材”。
- 预期结果：进入食材工作区并打开空白的“新增食材”表单。
- 实际结果：进入食材工作区后重新弹出刚关闭的“牛奶”详情；“新增食材”按钮只执行普通工作区导航，持久化的详情视图和已选食材因此重新生效。
- 根因：`HomeMobileDashboard` 的“新增食材”按钮直接发送 `{ workspace: 'ingredients' }`，绕过了食材工作区的一次性语义导航请求；食材工作区会恢复 `workspaceView` 和 `selectedIngredientId`，因此旧详情优先于按钮文案承诺的新建动作。
- 修复：新增 `create` 食材导航请求，由首页 handler 生成单调递增的 `requestId`；食材工作区消费该请求时调用既有 `openCreateView()`，一次性清空编辑对象、持久化草稿和图片生成状态，再打开新增表单。没有增加新的产品行为。
- 自动化验证：新增导航合同测试，证明首页新增动作生成 `target: create` 并进入食材工作区；新增移动首页组件测试，证明按钮调用专用新增入口而不是普通导航。
- 浏览器回归：按原路径重新打开并关闭“牛奶”详情，再从首页点击“新增食材”；实际打开标题为“新增食材”的空白表单，食材名称为空、默认规则复位，旧详情没有重现；390×844 无横向溢出。

## BUG-004：从非首页工作区启动时侧边栏显示错误家庭数据

- 严重度：P1（常驻应用壳把已有家庭显示成 0 位成员，并长期缺失本周协作数据；同一登录会话切换工作区后数值又变化）
- 修复方案确定性：97%
- 浏览器复现路径：Chrome 桌面端登录后恢复到上次停留的“食材”工作区 → 查看常驻侧边栏家庭信息 → 点击“首页”后再次查看同一区域。
- 预期结果：侧边栏作为全局应用壳，在任意工作区都加载并显示同一份家庭成员数和本周协作摘要。
- 实际结果：食材页显示“0 位成员 / 本周协作 --”；切到首页后变成“4 位成员 / 本周协作 0 次”，控制台没有报错。
- 根因：`AppShell` 在所有主工作区都渲染成员数和协作摘要，但 `useAppWorkspaceQueries` 把成员查询限定在部分页面、把活动高亮查询限定在首页和家庭页；未启用查询时，view model 又把缺失成员数据映射为 0、把缺失摘要映射为 `--`。
- 修复：和原本全局加载的家庭基本信息一致，认证后始终启用成员与活动高亮这两项壳级查询；成员查询继续参与首次启动 loading，避免在真实成员数返回前短暂渲染“0 位成员”，活动摘要仍不阻塞启动。
- 自动化验证：将工作区查询测试改为证明“食材”工作区也会各加载一次成员列表与 5 条活动高亮摘要；先确认旧实现红灯，再确认修复后 17 个查询范围用例全部通过。
- 浏览器回归：保持“食材”为持久化工作区后整页刷新以重建查询缓存；页面仍停留在食材页，侧边栏直接显示“4 位成员 / 本周协作 0 次”。Chrome 网络事件确认同路径发出 `/api/members` 与 `/api/activity-highlights?limit=5`，控制台无 warning/error。

## BUG-005：未登记过库存的采购项被标成“库存平稳”

- 严重度：P2（采购决策卡同时给出“未登记库存”和“库存平稳”两个互相矛盾的结论，容易让用户忽略需要首次入库的食材）
- 修复方案确定性：97%
- 浏览器复现路径：Chrome 桌面端 → 食材 → 采购 → 查看“甜虾刺身”采购卡；再切到“库存”查看同名食材。
- 预期结果：没有任何库存记录的已关联食材应使用现有统一库存状态“已空或未登记”，不能宣称库存平稳。
- 实际结果：采购卡同时显示“库存 未登记库存”和绿色“库存平稳”；库存页显示同一食材“未登记 / 总库存 0盒 / 0 批次 / 0 条提醒”。
- 根因：`buildShoppingCards` 已调用统一的 `buildInventoryCardStatus`，但渲染字段没有使用计算结果，而是把“没有库存提醒”直接映射为“库存平稳 / stable”；无记录食材恰好没有提醒，因此落入错误分支。
- 修复：当已关联食材没有可用库存数量汇总时，采购卡复用统一库存状态的“已空或未登记”标签，并使用中性状态；其他有库存、提醒和成品采购分支保持不变。
- 自动化验证：新增模型边界用例，先证明“0 库存记录 + 0 提醒”的采购卡错误返回“库存平稳 / stable”，修复后定向模型测试 40/40 通过。
- 浏览器回归：按“食材 → 库存 → 查看甜虾刺身 → 采购 → 查看甜虾刺身”原路径复测；采购卡现显示“库存 未登记库存 / 已空或未登记”，不再出现“库存平稳”，Chrome 控制台与失败请求事件均为空。

## BUG-006：家庭成员卡把全部历史活动显示为“今天记录”

- 严重度：P1（成员卡把累计历史活动误报成单日活动，数值可达数百次，直接破坏家庭协作数据可信度）
- 修复方案确定性：99%
- 浏览器复现路径：Chrome 桌面端 → 家庭 → 等待“家庭活动”加载完成 → 查看当前用户林然的成员卡。
- 预期结果：“今天记录”只统计 Asia/Shanghai 业务日 2026-07-29 内由当前用户产生的活动。
- 实际结果：成员卡显示“今天记录 830 次”，但页面最新家庭活动停在 7 月 22 日；只读数据库查询确认 7 月 29 日该用户活动数为 0。
- 根因：家庭页为活动列表加载全部 `/api/activity-logs`；`buildAppFamilyViewModel` 只按 `actor_id` 过滤后直接计数，没有按日期过滤，却把结果作为 `currentUserRecentLogs` 交给固定文案“今天记录”。
- 修复：复用统一的 `businessDateKey`，按 Asia/Shanghai 将每条活动时间转换为业务日期，只计入当前业务日且属于当前用户的记录；App 注入与首页一致的业务日期，使一次渲染内口径稳定且测试可控。
- 自动化验证：修改模型用例加入同一用户的一条历史活动，先确认旧实现返回 2 而今日应为 1，修复后定向测试 5/5 通过。
- 浏览器回归：按原路径在家庭页等待活动加载；成员卡现显示“今天记录 0 次”，与只读数据库对 2026-07-29 Asia/Shanghai 窗口的计数 0 一致；Chrome 控制台与失败请求事件均为空。

## BUG-007：移动食材页静默隐藏第 5 项之后的采购待办

- 严重度：P1（手机是主要体验，但真实待办在移动端完全不可见、不可查看也不可入库，用户会误以为清单已处理完）
- 修复方案确定性：99%
- 浏览器复现路径：Chrome 390×844 → 食材 → 滚动到“采购待办 6 项”区域 → 对照桌面“食材 → 采购”的完整清单。
- 预期结果：移动端 6 项待办均可达，或存在明确的分页/查看更多入口。
- 实际结果：标题显示 6 项，但 DOM 只渲染 4 张卡（三文鱼 3 张、鸡蛋 1 张）；桌面可见的“甜虾刺身”和“番茄”在移动端没有卡片，也没有查看更多、分页或独立完整清单入口。
- 根因：`useIngredientWorkspaceData` 对移动采购卡硬编码 `pendingShoppingCards.slice(0, 4)`；移动摘要按钮只滚动到同一列表，页面没有任何机制访问被截掉的记录。
- 修复：移动采购列表直接使用全部 `pendingShoppingCards`，继续复用现有排序、分组和抽屉，不改变待办含义或操作流程。
- 自动化验证：新增源码合同回归约束，先确认旧实现因存在四项截断而失败，移除截断后食材模型测试 41/41 通过。
- 浏览器回归：Chrome 390×844 按原路径复测；“采购待办 6 项”现渲染 6 张卡，“甜虾刺身”和“番茄”均各出现 1 次。打开“甜虾刺身”抽屉还验证 BUG-005 的移动展示为“库存状态 已空或未登记 / 当前库存 未登记库存”；页面 `scrollWidth` 与 390px 视口一致，无横向溢出。

## BUG-008：一次性“新增食材”导航在工作区重挂载后被再次执行

- 严重度：P1（用户通过普通导航重进食材时被强制带回已经关闭的新增表单，主导航语义失真）
- 修复方案确定性：99%
- 浏览器复现路径：Chrome 390×844 → 首页点击“新增食材”→ 关闭空白新增表单返回食材 hub → 点击底部“首页”使食材工作区卸载 → 再点击底部“食材”普通进入。
- 预期结果：一次性新增命令只执行一次；关闭表单并离开后，普通进入食材应显示 hub。
- 实际结果：App 层仍保存旧 `create` 请求；食材工作区重新挂载后，本地已消费 ref 回到 `null`，同一请求再次调用 `openCreateView()`。
- 根因：一次性导航请求的所有权在 App 层，但消费状态只保存在会随食材工作区卸载的本地 ref 中，成功执行后没有按 `requestId` 清除源请求。
- 修复：导航层新增按 `requestId` 原子清除请求的消费函数；食材工作区在 catalog/detail 状态导航完成或 create/shopping/priority 副作用真正执行后回报消费。ID 不匹配时不清除更新的请求，避免旧回调覆盖新导航。
- 自动化验证：新增导航合同回归用例，旧实现因缺少消费函数失败；修复后证明消费 `create` 请求会把 App 状态恢复为 `null`。定向导航与模型测试共 56/56 通过。
- 浏览器回归：Chrome 390×844 按原路径执行“新增食材 → 关闭 → 首页 → 普通进入食材”；重挂载后停留在手机食材页，`新增食材` dialog 数量为 0。

## BUG-009：仅剩过期批次的采购卡被降为中性状态

- 严重度：P2（危险文案配中性色，桌面端还会丢失专门的过期补充说明，削弱过期库存提示）
- 修复方案确定性：98%
- 浏览器复现路径：家庭中存在一个已关联食材，其所有剩余批次均已过期且同时有待采购项 → Chrome 进入“食材 → 采购”查看该采购卡。
- 预期结果：采购卡显示“临期或过期”并保持危险状态，桌面说明提示优先补充并入库。
- 实际结果：统一库存状态已判定为 `danger`，但采购卡因可用数量汇总为空又把 tone 覆盖成 `muted`，形成危险文案配中性色。
- 根因：`quantitySummaries` 只统计未过期可用批次，不能区分“从未登记”和“仍有过期剩余批次”；采购卡用该数组为空直接判断中性状态，覆盖了 `buildInventoryCardStatus()` 已得出的危险语义。
- 修复：采购卡直接复用统一库存状态的 tone；仅将该模型特有的 `empty` 映射为采购卡的 `muted`，`danger`、`warning` 和 `stable` 均保持原语义。
- 自动化验证：新增“已关联采购项 + 仅剩过期批次 + 可用汇总为空”模型用例；旧实现实际返回 `muted`，修复后返回“临期或过期 / danger”，定向导航与模型测试共 56/56 通过。
- 浏览器回归：未为该边界场景修改数据库或直接调用 API 构造数据；当前家庭没有同时满足“仅剩过期批次 + 已有关联待采购项”的现成记录，因此以同一浏览器可达状态的模型回归覆盖，未声称完成数据场景浏览器回归。
