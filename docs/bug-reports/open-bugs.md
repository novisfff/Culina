# 待确认 Bug

> 仅记录修复方案确定性低于 80% 的问题，不在本轮修改实现。

## OPEN-001：全局搜索中存在用户无法区分的重复餐食计划

- 修复方案确定性：72%（低于 80%，不修复）
- 浏览器复现路径：Chrome 桌面端首页 → 打开“全局搜索”→ 输入“牛奶”→ 查看结果列表中的餐食计划。
- 预期结果：每条搜索结果都能让用户识别它代表的具体对象；如果业务不允许同一食物在同一日期、餐次重复计划，则搜索结果不应出现重复对象。
- 实际结果：列表同时显示两条完全相同的“盒装牛奶 / 成品 / 2026-07-16 · 晚餐 · 已完成”，可见文案、匹配原因和 DOM 属性均无法区分。
- 调查记录：只读数据库查询确认它们是两个不同 ID 的真实 `food_plan_items`，食物、日期、餐次、状态和空备注相同，创建时间分别为 2026-07-17 03:20:28 与 05:19:30；不是搜索索引把同一 ID 返回两次。
- 不修复原因：当前数据模型没有同一食物/日期/餐次唯一约束，一个餐次也允许多项食物；现有规范不能确定正确行为应是禁止/合并重复计划、搜索层去重，还是在结果中增加创建时间等区分信息。任一实现都可能隐藏合法记录或扩展产品行为。

## OPEN-002：采购清单存在三条用户无法区分的“三文鱼”待办

- 修复方案确定性：68%（低于 80%，不修复）
- 浏览器复现路径：Chrome 桌面端 → 食材 → 采购 → 查看“待采购清单”。
- 预期结果：如果同一菜谱来源的同名、同数量采购需求代表同一待办，则只显示一条或合并数量；如果它们是合法的独立需求，卡片应提供足够信息让用户区分。
- 实际结果：页面连续显示三条完全相同的“三文鱼 / 1块 / 来自菜谱：清蒸三文鱼”，库存、关联状态和操作也一致，用户无法判断应完成一条还是三条。
- 调查记录：只读数据库查询确认这是三条不同 ID 的真实待办，均为未完成、数量 `1.00`、单位“块”、相同原因，创建时间分别为 2026-05-14 10:45:03、2026-05-15 01:36:13、2026-05-15 02:38:49；不是 React 重复渲染。三个记录都没有持久化 `ingredient_id`/`food_id`，当前前端按同名食材做兼容关联。后端创建合同没有重复约束或合并规则。
- 不修复原因：现有实现允许用户或不同入口重复添加采购项，源码与规范无法确定正确语义是创建时幂等、展示时合并、保留独立记录并显示创建来源/时间，还是仅修复某个未知历史入口。直接去重可能隐藏用户确实想买三份的合法记录，属于产品行为扩展。
